# ADR 0001: Application and framework package boundaries

Status: Accepted for the initial development foundation
Date: 2026-09-11
Scope: Phase 1A

## Context

Careminate needs a reusable framework package and an application that
consumes it. Their dependency direction must remain explicit.

The initial repository is a development workspace. It is not a released
framework distribution or a production application.

## Decision

The repository root is the careminate/caremi Composer project.

The framework directory is the careminate/framework Composer library.

The application depends on the framework. The framework must not depend
on application classes, application configuration files, or the root
application's directory layout.

Composer owns autoloading:

| Namespace | Owning package | Source directory |
| --- | --- | --- |
| App\ | careminate/caremi | app/ |
| Careminate\ | careminate/framework | framework/src/ |

Paths in each Composer autoload declaration are relative to that
package's composer.json file.

Source directories are introduced with their first implementation
files. This unit does not add empty source files or placeholder classes.

## Local package resolution

The root manifest declares a canonical path repository at framework.

The repository options explicitly map careminate/framework to dev-main.
This mapping avoids dependence on the surrounding Git branch name.

The framework manifest does not declare a version. A future package
release will obtain its version from the release process and Git tags.

The root's explicit dev-main requirement permits the unreleased local
framework package. The root minimum-stability remains stable for other
dependencies.

This development requirement must be replaced with an approved stable
release constraint before a production application release.

Composer chooses whether to link or mirror the local package according
to the environment. The repository does not force Windows users to
create symbolic links.

When Composer mirrors the package, framework source edits require a
package refresh before the application can consume them:

    composer reinstall careminate/framework

When Composer links it, source edits are visible through that link.

## Supported PHP versions

Both packages require:

    ~8.4.0 || ~8.5.0

This permits PHP 8.4 and PHP 8.5 patch releases.

Later minor branches require deliberate compatibility evaluation and a
manifest update. Older XAMPP runtimes do not justify lowering the baseline.

No simulated config.platform.php value is configured. Installation
checks the PHP runtime actually running Composer.

## Dependency ownership

Framework runtime dependencies belong in framework/composer.json.

Application runtime dependencies belong in the root composer.json.

Development tools will be introduced in Phase 1B with explicit version
constraints and explanations.

The root does not duplicate the framework's production autoload mapping.
This preserves package-level integration through Composer.

Composer plugins are disabled in the root project. A future plugin
dependency requires a documented, package-specific allow-list change.

## Dependency locks

The root composer.lock must be generated by Composer and committed after
successful dependency resolution. It must not be authored manually.

Subsequent development and CI installations use composer install against
the committed lock file. Dependency updates are deliberate changes.

If a separate framework development lock file is introduced, it must
also be generated, committed, and validated for that workflow.

Lock files are intentionally not ignored.

A path dependency lock identifies package metadata; it does not freeze
the framework source tree. Reproducibility also requires the matching
repository commit.

## Licensing

The initial manifests declare proprietary pending the owner's explicit
distribution license decision.

This declaration grants no open-source permissions.

A public release requires a selected license, the corresponding license
file, and consistent package metadata.

## Alternatives considered

### One combined package

Rejected because it couples application ownership and framework
distribution.

### Duplicate framework autoloading in the root

Rejected because it can conceal a broken framework package manifest.

### Forced symbolic links

Rejected because local Windows permissions and filesystem support vary.

### Stable version assigned to unfinished code

Rejected because local development must not imply that a release exists.

## Consequences

The framework can evolve as an independently consumable package.

The development application exercises the package boundary through
Composer.

Package installation, namespace resolution, and Windows/Linux behavior
still require executable verification.

No runtime APIs or application bootstrap are introduced by this decision.
